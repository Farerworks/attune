### 0.1 시작 전 기준점 확인 — `git pull` 하지 말 것

pull은 기준점을 *확인*하는 게 아니라 *바꾼다*.
```
git status --porcelain     # 추적 대상 변경이 없어야 한다
git fetch origin
git rev-parse HEAD
git rev-parse origin/main
```
`HEAD`와 `origin/main`이 **둘 다** `fc76fb6533195a4fa61c211efdd597e1ba1e6ba0`(테스트 868 = 865 passed + 3 expected fail)이어야 한다. **어긋나면 `checkout`·`reset`·`merge`·`rebase` 하지 말고 그 상태 그대로 보고**한다 — 기준점은 본부와 YS가 판단한다.

### 0.2 전용 작업 브랜치를 만든다 — 이 판은 `main`에서 하지 않는다

**이 저장소는 `main` push가 Vercel Production 자동 배포를 유발한다.** 직전 판에서 `origin/main = fc76fb6` push 후 앱 Settings 푸터가 `fc76fb6`으로 확인돼 **사실로 확인된 동작**이다. 따라서 `main`에서 작업하면서 「Production 배포 없음」은 성립하지 않는다.

기준점이 맞으면 `fc76fb6`에서 전용 브랜치를 만들고 거기로 이동한다.
```
git checkout -b fix/100b-fix5 fc76fb6533195a4fa61c211efdd597e1ba1e6ba0
git rev-parse --abbrev-ref HEAD    # fix/100b-fix5 여야 한다
```
브랜치명은 **정확히 `fix/100b-fix5`**다. 바꾸지 않는다.

**이 판의 커밋 3개(브리프 보관 · 코드+테스트 · 완료 보고서)는 전부 `fix/100b-fix5`에만 만든다.** push도 아래 한 줄로만 한다.
```
git push -u origin fix/100b-fix5
```
**`origin/main`에 merge·push·rebase·cherry-pick 하지 않는다.** `git checkout main`으로 돌아가지 않고, `main`을 건드리는 어떤 명령도 실행하지 않는다. 작업이 끝나도 `main`은 `fc76fb6` 그대로여야 한다.

**Preview 배포 주의**: 브랜치 push로 Vercel **Preview** 배포가 자동 생성될 수 있다. 생성되면 **Production과 구분해서** 보고한다(`Preview: <URL 또는 상태> / Production: 미배포`). **Preview 결과를 Production PASS의 근거로 쓰지 않는다.**

직전 판(`BRIEF-100B-FIX4-C`)이 completion 판정을 **「인용·보고 영역과 사용자 직접 발화 영역을 분리한 뒤 마지막 유효 의도로 결정」** 구조로 교체했다. 인용·문장 간 취소·후치 부정은 그때 닫혔다.

**그런데 시제·상 축(완료·과거 보고 / 숙고 / 의도 선언)의 제외 규칙이 한 개도 들어가지 않았다.** FIX4-C 브리프 §1.1이 「`COMPLETION_EXCLUSIONS` 내용 무변경」이라고 못박았고, 그 배열은 지금 **2개**뿐이기 때문이다. 이건 본부 브리프의 누락이었다.

그 결과 **오분류 26건이 그대로 남아 있다.** 전부 「이미 썼다 / 쓸까 고민이다 / 내가 쓰겠다」인데 완성물 요청으로 잡힌다.

## 1. 변경 사양 (`src/app/api/ask/route.ts` — 배열 하나)

### 1.1 `COMPLETION_EXCLUSIONS`를 2개 → 8개로

기존 2개는 **순서·내용 그대로 두고**, 그 뒤에 아래 6개를 **이 순서 그대로** 붙인다.

```ts
export const COMPLETION_EXCLUSIONS: RegExp[] = [
  /(?:안|못)\s*(?:써|적어|만들어|뽑아)/,                              // (기존 1)
  /(?:써|적어|만들어|뽑아)\S*\s*(?:할까|말까|될까)/,                   // (기존 2)

  // ── BRIEF-100B-FIX5 — 시제·상(相) 축. 이 절은 요청이 아니라 보고·숙고·의도다. ──
  // 완료·과거 보고: 이미 썼거나 보냈다는 서술.
  /(?:써|적어|만들어|뽑아)(?:서)?\s*(?:봤|놨|뒀|보냈)/,               // 써봤어 / 써놨어 / 써뒀어 / 써(서) 보냈어
  // `줬`은 완료형이지만 `줬으면`은 간접 요청이다 — 부정 전방탐색으로 요청만 살린다.
  /(?:써|적어|만들어|뽑아)줬(?!으면)/,                                // 써줬어 O / 써줬으면 좋겠어 X(통과)
  /(?:써|적어|만들어|뽑아)줘서\s*(?:고마|감사|좋았|다행)/,             // 써줘서 고마워
  /(?:써|적어|만들어|뽑아)준\s*(?:거|것|건|게)/,                       // 써준 거 보냈어
  // 의도 선언: 사용자가 자기가 쓰겠다고 말하는 형태.
  /(?:써|적어|만들어|뽑아)(?:볼|보|놓을|둘|줄)?\s*(?:게|야지|려고)/,   // 써볼게 / 써둘게 / 써야지 / 써보려고
  // 숙고: 사용자가 자기가 쓸지 고민하는 형태.
  /(?:써|적어|만들어|뽑아)(?:볼|놓을|둘)(?:까|지)/,                    // 써볼까? / 써볼지 고민이야 / 써놓을까?
];
```

주석은 위에 적힌 것을 **그대로** 넣는다.

### 1.2 적용 지점 — 이미 그 자리에 있다. 코드를 옮기지 말 것

`COMPLETION_EXCLUSIONS`는 `detectCompletionRequest` 안에서 **절 단위 `nonRequest` 판정**에만 쓰이고 있다. 배열만 늘리면 6개도 같은 자리에서 동작한다.

```
① splitSentences                     ← 무변경
② splitCompletionParts (quote/user)  ← 무변경
③ 절 라벨:  FORBID → [요청 여부] → CANCEL
                        ↑ 여기의 nonRequest 판정에 8개가 쓰인다
④ user 절만 잔류                      ← 무변경
⑤ 마지막 유효 의도                    ← 무변경
```

**`detectCompletionRequest`·`splitCompletionParts`·`detectAskMode`의 코드를 한 줄도 바꾸지 않는다.** 이 판의 diff는 `COMPLETION_EXCLUSIONS` 배열 안과 `route.test.ts`뿐이어야 한다.

**전역 exclusion으로 되돌리는 것을 금지한다.** 즉 `detectAskMode`나 함수 바깥에서 입력 전체에 `COMPLETION_EXCLUSIONS`를 걸지 않는다. 전체에 걸면 `메시지 써봤는데 친구에게 새로 하나 써줘` 같은 **혼합 의도 요청이 다시 죽는다**(전례: 혼합 양성 7건 전건 실패).

### 1.3 설계 근거 — 구현 시 바꾸지 말 것

1. **`줬(?!으면)`의 부정 전방탐색.** `줬`은 완료형일 때도 있고 간접 요청(`써줬으면 좋겠어`)일 때도 있다. 빼면 한국어에서 매우 흔한 요청이 통째로 죽는다.
2. **`(?:볼|보|놓을|둘|줄)?`의 선택 그룹.** `써볼게`·`써보려고`·`써야지`를 한 패턴으로 덮는다. `보`를 빼면 `써보려고`가 샌다.
3. **숙고는 `(?:볼|놓을|둘)(?:까|지)`, 의도는 `(?:게|야지|려고)`로 갈라 둔다.** 합치면 `써볼게`(의도)와 `써볼까`(숙고)의 경계가 흐려진다.
4. **`할까|말까|될까`(기존 2)와 `볼까|놓을까`(신규)는 중복이 아니다.** 전자는 `써야 할까`, 후자는 `써볼까`를 잡는다.
5. **관찰되지 않은 어미를 추측으로 넣지 말 것**(`던데`·`더라고`·`거든` 등). 확장은 실사용 관측 후 별건.

### 2.1 현재 테스트에 잘못 고정된 기대값을 교정한다

직전 판에서 `TESTSET` v1.1의 **L·E군에 기대값 열이 없었다.** 그래서 `route.test.ts`의 E군 표에 **당시 구현 출력이 기대값으로 적혔고**, 오분류 26건이 「정상 동작」으로 굳었다. 예: `['E-037', '답장 써봤어', 'completion']` — **제품 기대값은 `null`이다.**

- **`route.test.ts`의 모든 분류 사례 기대값을 `TESTSET` v1.2의 「제품 기대값」 열로 맞춘다.** 어긋나는 행은 전부 교정 대상이다.
- **v1.2의 `현재 실제값` 열을 기대값으로 쓰지 말 것.** 그 열은 `fc76fb6`의 실측이며 **참고 정보**다.
- 교정 대상 26행: `E-010` · `E-012` · `E-037`~`E-048` · `E-050`~`E-057` · `E-073`~`E-075` · `E-077`.

### 2.2 분류 사례 테스트 — ID를 그대로 쓴다

- `TESTSET` v1.2 §2의 **X군 전건**. **범위 표기(`X1-…`~`X5-…` 같은 축약)로 축을 생략하지 말고, 문서에 기록된 모든 X ID를 그대로 쓴다.**
- §3의 **L군 전건**, §4의 **E군 전건**.
- 테스트 설명에 ID를 그대로 쓴다(예: `E-037 답장 써봤어 -> null`).
- **ID 없는 분류 사례를 임의로 추가하지 않는다.** 이 금지는 **분류 사례 테스트에만** 적용된다.

## 4. 금지사항
- **`main`을 건드리지 말 것.** `git checkout main` · `git merge` · `git push origin main` · `git rebase main` · `cherry-pick` 전부 금지. 이 판의 커밋은 **`fix/100b-fix5`에만** 존재해야 하고, 종료 시점에 `origin/main`은 `fc76fb6533195a4fa61c211efdd597e1ba1e6ba0` 그대로여야 한다.

**신규 FN 1건 — `E-080` `오늘 보낼 메시지 좀 써줘 어제 건 써봤어`**
지금 이 문장이 통과하는 것은 **완료 표지를 아예 보지 않기 때문**이며, 옳은 이유로 맞은 게 아니다. 제외를 넣으면 문장부호가 없어 한 절로 묶이고, **절 단위 판정은 절 안의 순서를 보지 않으므로** 완료 표지가 요청을 이긴다. 이미 알려진 미지원(부호 없는 역순 혼합)과 **같은 구조의 실패**다.

**절 안의 순서까지 보는 확장은 이 판에서 하지 않는다.** 판정 구조를 또 한 겹 바꾸는 일이고 별도 게이트가 필요하다.

**측정 범위**: 현재 정의된 테스트 계약에서 중복 제거된 고유 입력은 **115건**이며 판정 대상은 **112건**이다. 자연어 전체 입력 공간은 정의할 수 없으므로, **이 115건 이외의 조합과 표현은 미측정**이다. 한국어의 시제·상 어미는 §1.1이 열거한 형태보다 넓다.

**검증 수준**: 본부 자체 검토 + 스크립트 실행 확인. **독립 검수 미수행.**

**구조 대안 비교**: 「절 단위 상태 7종으로 구조화」하는 안과 실측 비교했고 **115건에서 판정이 갈리는 사례가 0건**이었다. 결과가 같으면 변경 표면이 작은 쪽을 택한다는 기준으로 이 안을 골랐다.
