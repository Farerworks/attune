# BRIEF-100B-FIX v1 — Ask 응답의 사실성·출력 계약 집행

## 0. 맥락 (자기완결)
Attune(github.com/Farerworks/attune, 랩 PC `~/projects/attune`). 시작 전 `git pull` — 기준 = 현 origin/main `04bb008`(테스트 610).

BRIEF-100B가 Ask 응답 검증 파이프라인을 넣었고, 실앱 SMOKE에서 **재소개 억제는 통과**했다(정체성 단어 누적 0회). 그러나 같은 실행에서 **다섯 가지 결함**이 실제 화면에 나왔다. 아래는 관측된 출력 원문이다.

| # | 실제 출력 | 무엇이 잘못됐나 |
|---|---|---|
| 1 | 사용자 "연락**하기로 했어**" → 앱 "연락**하고 나서** 은우가 어떤 반응을 보이던가요?" | 계획을 완료로 취급 |
| 2 | "은우가 **좋아하는** 커피나 가벼운 산책" | 취향 정보 0인데 아는 것처럼 단정 |
| 3 | "그 선택이 은우에게 참 반가운 숨 고르기가 **되어줄 거예요**" | 상대의 미래 반응 보장 |
| 4 | "문장 2개만" 요청에 두 줄 + "보내고 나서 은우 반응은 어땠는지 알려줘요." | 출력 계약 위반 |
| 5 | "…은우의 **진짜 마음**을 읽는 데 도움이 될 거예요" / 추천 칩 "…**진짜 이유**는 뭘까?" | 숨은 진실을 알 수 있다는 프레이밍 |

**핵심 진단(저장소 실측 — §4.5)**: 4번은 계약이 없어서가 아니다. `STRICT_SCRIPT_PATTERNS`가 "문장 2개"를 정상 감지하고(`COUNT_WORD`에 `\d+` 포함), `STRICT_SCRIPT_BLOCK`은 이미 **"No … followUp"** 을 명시한다. 그런데 `validateAskAnswer`는 strict_script에 대해 **`parts` 사용 여부만** 검사한다(`strict_script_parts`) — **followUp 유무와 줄 수는 검사하지 않는다.** 즉 **기존 계약이 집행되지 않고 있다.** 이 판의 상당 부분은 새 계약 추가가 아니라 **집행 추가**다.

이 판은 **Ask 범위 한정**이다. Briefing·카피 P0·`[sync]` 백업 결함·`clearAllData`의 `attune.ask.memory` 누락은 다루지 않는다(§5-3).

## 1. 변경 사양 — 행동 요구 5 (구현 단위는 재량, 다섯 곳으로 나눌 필요 없음)

### F1. 시간 상태 보존
사용자 발화의 **계획 / 실행 / 상대 반응**을 구분한다. 아직 일어나지 않은 단계의 결과를 묻거나 전제하지 않는다.

### F2. 출력 계약 집행
사용자가 개수·형식을 지정하면 그것이 상담 스타일보다 우선한다. **사용자가 요청한 단위를 그대로 집행한다.**

| 사용자 요청 | 출력 계약 |
|---|---|
| `문장 N개` · `N sentences` | **정확히 N문장**, 각 문장을 **별도 줄**에 |
| `메시지 N개` · `멘트 N개` · `N messages` · `N lines` | **정확히 N개 메시지**, 각 메시지를 **별도 줄**에, 각 메시지는 자연스러운 범위에서 **최대 2문장**(`오랜만이야! 잘 지내?` 형태 허용) |

두 경우 모두 **번호·불릿·라벨·섹션 제목·`/` 구분자·`followUp`을 붙이지 않는다.**

**프롬프트 계약 정정(필수)**: `STRICT_SCRIPT_BLOCK`(route.ts:200)에서 **`plus at most one short sentence of framing`을 삭제**한다. "정확히 N개"와 "안내 한 문장 허용"을 동시에 두면 계약이 서로 충돌하고, 이번 SMOKE 실패가 그대로 재발한다. **명시적 개수 요청에서는 요청된 결과만 출력한다.**

### F3. `followUp` 처분 — 요청 유형별
| 요청 유형 | `followUp` |
|---|---|
| 완성 문구·목록·정확한 출력 요청 | **없음** |
| 근거가 부족한 상담 질문 | 관련 있는 것 **최대 1개** 허용 |
| 이미 사용자가 답한 사실을 다시 묻는 질문 | **금지** |
| 아직 발생하지 않은 결과를 묻는 질문 | **금지** (F1과 동일 근거) |

"연속 턴에서 전부 채워지면 실패" 같은 **기계적 빈도 기준은 쓰지 않는다.**

### F4. 사실과 추정의 경계
제3자의 **취향·속마음·미래 반응**을 근거 없이 만들어내지 않는다. 근거 순서: 사용자가 준 사실 → 대화 이력 → 관찰 패턴 → 차트. 차트는 가능성을 넓히는 보조 렌즈다.

- **금지**: 근거가 없을 때의 `은우가 좋아하는 X` — 앎의 주장
- **허용**: `X처럼 부담이 적은` (선택지형) / `평소 좋아한다고 말한 게 있다면` (사용자 사실 조건형)
- **허용**: 사용자가 **실제로 말한** 취향을 근거로 쓴 출력은 **정상 통과한다.** 앞선 턴에 `은우는 커피를 좋아해`라고 말했다면 이후 `은우가 좋아하는 커피`는 정상이며, **검증기·프롬프트가 이를 차단하거나 지워서는 안 된다.** 취향 언급을 일괄 회피하는 **과차단도 실패다.**
- **강제하지 않음**: 다만 **매 답변에서 저장된 취향을 반드시 언급하도록 강제하지 않는다.** 해자는 기억을 **필요할 때 자연스럽게 쓰는 것**이지 매번 꺼내는 것이 아니다.
- **금지**: 상대의 미래 반응 보장(`반가워할 거예요`, `마음의 문을 열 거예요`)
- **가능성 표현은 자동 통과가 아니다**: `~일 가능성이 커요`도 근거 없이 쓰면 추측이다. **사용자 사실이나 관찰된 맥락에 연결되고, 하나의 설명만 사실처럼 우선하지 않을 때** 통과한다.

### F5. 숨은 진실 프레이밍 억제
답변 본문·`followUp`·추천 칩 **어디에서도** 상대의 숨은 진실을 알아낼 수 있다는 **긍정적·확정적 주장**을 하지 않는다.

- 막을 것: `진짜 마음을 읽을 수 있다` / `진짜 이유를 알아낼 수 있다` / `반응 하나로 속마음을 확정할 수 있다`
- **통과시킬 것**: `진짜 마음을 한 번의 반응으로 알 수는 없어요` 같은 **부정형·한계 고지형**
- **구현 방식**: **프롬프트 1차 + 출력 검증기 2차.** **전역 단순 문자열 차단은 금지**한다 — 어휘가 아니라 **주장의 방향**을 본다. 검증기가 의미 방향을 안정적으로 구분하지 못하면, 복잡한 정규식을 억지로 만들지 말고 **프롬프트 규칙을 강화하고 명확한 위험 패턴만 최소 검출**한다.

### 회귀 방지 조건 (수정 대상 아님)
**정체성 단어 재소개 억제** — SMOKE에서 통과했다. 이번 판에서 깨지지 않아야 한다. 기존 라벨 세트·근거 우선순위·안전 게이트·호칭 미러링도 무회귀.
