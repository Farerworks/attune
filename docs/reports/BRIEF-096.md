## 2. 구현 요지

**safety.ts §1** — SAFETY-SPEC v1.2가 새로 제공한 8개 출처 URL 매핑(KR 112/119/109/1366, US 911/988/관계폭력/데이트폭력)을 `https://` 접두만 붙여 그대로 채웠다. 하나의 매핑이 여러 채널(전화·문자)에 걸쳐 재사용되는 경우(예: US 988의 전화·문자 행 둘 다 `988lifeline.org`) 그대로 양쪽에 적용했다. 다른 필드는 손대지 않았다.

**클라이언트 배선 (ask/page.tsx)** — `handleSend` 맨 앞에서 `detectWithContext([최근 발화 최대 3개, 새 입력])`을 검사한다. 트리거가 잡히면 그 즉시 `return`하여 **LLM 호출도, 쿼터 차감도, 스레드 저장도 일어나지 않는다** — 기존 "메시지를 낙관적으로 스레드에 먼저 쓰고 전송" 흐름보다 앞서 있기 때문에 위험한 문구 자체가 저장소에 닿지 않는다. 트리거된 상태는 `safetyCardState`(S1_SELF/S1_OTHER/S1_NARROW/S2/S3)라는 별도 컴포넌트 상태로만 관리하고, 이 상태가 있는 동안 하단 입력창 전체를 `SafetyPanel`로 교체한다(텍스트 입력창 자체가 사라지므로 "카드 표시 중 입력창 비활성"을 그대로 만족).

- **S1 카드**: 감정 인정 1줄(이번 브리프 §2가 정본, `safety.ts`가 아님) + `SAFETY_COPY_KO/EN`의 해당 질문 + 4버튼. `routeSafetyAnswer`를 그대로 사용해 다음 상태를 계산한다.
- **S1_NO**: 재진입 문장(5-4)을 대화 목록 맨 아래에 어시스턴트 말풍선 스타일로 보여주되, 이 문장은 `threads`/localStorage에 전혀 쓰지 않는 별도 상태(`safetyReentryText`)로만 존재한다. 동시에 막혔던 원문을 입력창에 그대로 복원하고, **자동 전송은 하지 않는다** — 사용자가 직접 다시 눌러야 전송된다. 이 재전송 1회에 한해 클라이언트 재검사와 서버 게이트를 모두 건너뛰는 `ackNextSend`/`safetyAck` 플래그를 함께 사용한다(§3 참고).
- **S1_NARROW**의 2·3번 선택지는 각각 S1_SELF/S1_OTHER로 전이해 해당 확인 카드로 바로 교체한다.
- **S2**: 중단 고지(5-6) + 임박성 질문 1개(계열별 5-5) + 3버튼(`예`/`아니요, 생각만이에요`/`답하기 어려워요` — KO는 이 브리프 §2 원문 그대로, EN은 기존 "hard to answer" 톤에 맞춰 새로 지음, §6에 명시) + `getSafetyContacts(country, situation)` 목록. `예`만 S3로 전이하고 나머지는 연락처 화면에 그대로 머문다(SAFETY-SPEC 5-5: 생각만=S2, 답하기 어려움=S2).
- **S3**: 최소 화면 — 긴급전화(KR 112·119 / US 911)를 대형 `tel:` 버튼으로 우선 배치, 자살·자해 또는 관계폭력 라인을 보조로. 세리프 폰트·글리프·모션 전부 없음(Inter만 사용).
- **국가**: 기본값은 UI 언어(`navigator.language`가 `ko`로 시작하면 KR, 아니면 US)로 정하고, `한국이 아닌가요?`/`Not in the US?` 링크로 전환 가능.
- **연락처 렌더링**: `call` 채널은 `tel:`, `text`(textCode 있음)는 `sms:번호?&body=코드`, `web`은 `sourceUrl` 또는 `https://값`으로 새 탭 링크.

**서버 배선 (api/ask/route.ts)** — 요청 스키마에 `safetyAck?: boolean`을 추가하고, saju 계산·LLM 호출보다 앞서 `detectSafetyTrigger(question)`을 검사한다. 트리거가 있고 `safetyAck`가 없으면 `{ safety: category }`만 반환하고 끝낸다 — **LLM을 아예 호출하지 않으므로** 클라이언트 우회(직접 API 호출 등) 방어가 된다. `PERSON_RULES`/`SELF_RULES` 두 블록 뒤에 SAFETY 지시문(이번 브리프 §3 원문 그대로, 바이트 수정 없음)을 공통으로 한 번만 삽입했다. BANNED 목록에 `사주상 충동적인`, `impulsive day in your chart` 2건을 추가했다.

## 3. 낙인 최소화 확인

`safetyCardState`·`safetyTrigger`·`pendingText`·`safetyReentryText`는 전부 `useState`로만 존재하고, 이 값들을 `threads`(→`saveThreads`→localStorage)에 쓰는 코드 경로가 없다. 안전 흐름을 타는 원문 메시지는 S1_NO로 "무해함"이 확인되어 사용자가 직접 재전송할 때만 비로소 정상적인 `handleSend` 경로(스레드 저장 포함)를 탄다 — 그 전까지는 어디에도 남지 않는다. 테스트 5건 중 1건이 이를 직접 검증한다.

## 4. 테스트

**클라 5건** (`ask/page.test.tsx`):
1. 트리거 메시지 → S1 카드 렌더 + `/api/ask` fetch 0회 + 잔량 표시 불변.
2. `"It's hard to answer"` → S2 진입, 기본(비한국어) 로케일에서 미국 `988` 연락처, 국가 전환 후 한국 `109` 연락처.
3. S1_NO → 재진입 문장 표시 + 입력창에 원문 복원 + `/api/ask` 미호출(자동 전송 없음).
4. 한국어 로케일 + "지금 위험할 수 있어요" → S3에서 `112 전화하기`/`119 전화하기`가 각각 `tel:112`/`tel:119`로 연결.
5. S1→S3까지 진행해도 `attune.ask.threads`에 위험 문구가 전혀 기록되지 않음.

**서버 4건** (`api/ask/route.test.ts`):
1. `buildAskSystem`이 3개 모드 전부에서 SAFETY 블록을 바이트 그대로 포함.
2. 트리거 + `safetyAck` 없음 → `generateJsonChat` 미호출, `{ safety: 'self' }` 반환.
3. 트리거 + `safetyAck: true` → 게이트 건너뛰고 LLM 정상 호출.
4. 트리거 없음 → `safetyAck` 유무와 무관하게 정상 진행.

## 7. 정직 보고

- **S1 카드 4번째 선택지가 390×844 화면에서 화면 하단에 가려짐**: "아 진짜 죽겠다"처럼 질문 문장이 길면 4개 버튼 중 마지막(`답하기 어려워요`)이 하단 탭바에 시각적으로 가려 안 보일 수 있다(스크린샷 ①에서 확인됨). 클릭/터치 자체는 여전히 가능함을 별도로 확인했지만(스크린샷 ②가 바로 그 버튼을 눌러서 나온 결과), 실제로는 사용자가 눈으로 못 보고 있을 위험이 있다 — 이 브리프의 지시 범위(배선)를 벗어나는 레이아웃 조정이라 이번엔 손대지 않았고, 후속 소소 브리프 대상으로 보고한다.
- **Playwright의 `page.click()`이 Send 버튼에서 일관되게 씹히는 현상을 겪었다** — 좌표·`disabled` 속성 모두 정상인데도 클릭 이벤트가 React 핸들러까지 닿지 않아, 검증 스크립트는 Enter 키 제출(기존에도 지원되던 정상 경로)로 우회했다. 실제 브라우저/실기기에서는 버튼 클릭이 표준적으로 동작하는 패턴이라 앱 버그로 보지 않지만, 확인을 못 했다는 사실 자체는 밝혀둔다.
- **S2 임박성 질문의 3버튼 EN 라벨**(`Yes` / `No, just thoughts` / `It's hard to answer`)은 SAFETY-SPEC과 이번 브리프 어디에도 영문 정본이 없어 직접 작성했다(KO는 브리프 §2 원문 그대로) — §6이 명시한 판단 근거다.
- **새로 채운 8개 출처 URL 중 7개(KR 4개 전부 + US 988/800-799-7233/866-331-9474 계열)는 실접속으로 확인**했고 전부 해당 기관 공식 페이지로 일치했다. **US 911(`911.gov/calling-911`)만 자동 접속이 403으로 차단**되어 직접 확인은 못 했지만, 웹 검색으로 `911.gov`가 National 911 Program 공식 사이트이고 `/calling-911/` 경로가 실재함을 교차 확인했다.
- 서버 게이트는 "마지막 사용자 메시지"(`question` 필드)만 검사한다 — `history` 배열 안의 과거 발화까지 서버가 재검사하지는 않는다. 클라이언트의 `detectWithContext`가 최근 발화 창을 이미 함께 보므로 이중 방어 목적상 충분하다고 판단했다.
