## 2. 구현 요지

### 사전 발견 — §4.5식 실측 결함 1건 추가
지시서 §2의 예시 `보낼 메시지 2개만 써줘`를 기존 `STRICT_SCRIPT_PATTERNS`가 감지하지 못하는 걸 코드 확인으로 발견했다(`멘트`만 있고 정식 단어 `메시지`가 없었음). `문장`/`메시지`/`멘트`/영문 패턴 옆에 `메시지\s*COUNT\s*개`를 추가했다 — 기존 패턴 대체 아님, 순수 추가.

### F1 시간 상태 보존 — 프롬프트 전용
새 `TEMPORAL STATE` 블록(person 모드)을 PERSON_RULES 끝에 추가: 계획(`~하기로 했어`)은 완료가 아니며, 사용자가 실제로 일어났다고 보고하기 전까지 상대 반응을 묻거나 안다는 듯 쓰지 않는다. **출력 검증기는 두지 않았다** — "완료 전제 질문"을 텍스트만 보고 신뢰성 있게 판별할 정규식이 없고, 목(mock) LLM으로는 실제 모델의 시제 추론을 시험할 수 없기 때문. 테스트는 프롬프트에 새 규칙 문구가 실제로 존재하는지로 고정했다.

### F2 출력 계약 집행 — 프롬프트 + 검증기 (지시서가 명시한 "계약은 있는데 집행이 없다" 케이스)
- `STRICT_SCRIPT_BLOCK`에서 `plus at most one short sentence of framing` 삭제(§5 결재), 문장/메시지 단위 구분과 번호·불릿·라벨·"/" 금지를 명시.
- 신규 `parseScriptRequest()` — 감지에 쓰인 것과 같은 패턴으로 요청 개수·단위(문장/메시지)를 역산.
- `validateAskAnswer()`에 새 `script_contract` 위반 3종(count/format/followup) 추가 — strict_script 모드 + `{text}` 형태일 때만 검사(`parts` 형태는 기존 `strict_script_parts`가 이미 처리).
- 재생성 1회로도 안 고쳐지면 최종 처분: `followup` → 안전하게 키 제거, `count`(초과분만) → 앞에서부터 요청 개수만큼 자르기(부족분은 지어낼 수 없으니 그대로 두고 로그만), `format` → 안전한 자동 수정이 없어 그대로 두고 로그만(soft).

### F3 followUp 처분 — 프롬프트 강화 + F2 검증기 재사용
FOLLOW-UP RULE에 "완성된 출력을 줬으면 followUp 생략", "아직 일어나지 않은 결과를 묻지 않음" 문장 추가(전 모드 공통). "완성 문구·정확한 출력 요청 → followUp 없음" 행은 F2의 script_contract(followup) 검증기가 그대로 집행한다(스크립트 요청 자체가 "정확한 출력 요청"이므로). 나머지 행(근거부족 최대1개/기답변 재질문 금지)은 기존 문구 무회귀로 확인.

### F4 사실과 추정의 경계 — 프롬프트 전용
새 `EVIDENCE FOR CLAIMS ABOUT THEM` 블록(person 모드): 사용자가 실제로 말하지 않은 취향·속마음·미래반응을 사실처럼 쓰지 않되, 사용자가 실제로 말한 취향은 자연스럽게 쓰고 매번 강제로 언급하지도 않는다. 가능성 표현도 근거 연결이 필요하다는 문장, 미래 반응 보장 금지(관측된 결함 문구 `되어줄 거예요` 포함) 명시. **검증기는 두지 않았다** — "사용자가 실제로 이 취향을 말했는가"를 신뢰성 있게 판정하려면 엔티티 매칭이 필요한데, 얕은 구현은 과차단(지시서가 명시적으로 금지) 또는 과소검출 둘 다 위험이 크다고 판단해 프롬프트만으로 처리했다.

### F5 숨은 진실 프레이밍 억제 — 프롬프트 + 최소검출 검증기 (지시서 §1 F5 명시 방식)
- 새 `NO HIDDEN-TRUTH FRAMING` 블록(person 모드).
- 신규 `findHiddenTruthFraming()` — **전역 문자열 차단이 아니라 방향성 판정**: `진짜 마음`/`진짜 이유`/`숨은 진심`/`숨은 진실`/`속마음 확정` 같은 주제어가 등장하면서 같은 문장 안에 부정·한계 표현(`없`/`어렵`/`힘들`/`모르`/`아니`)이 **전혀 없을 때만** 위반으로 잡는다. 부정형(`알 수는 없어요`)은 그대로 통과한다.
- 검사 범위는 답변 본문(`text`/`parts[].text`) + `followUp` 전부 — "추천 칩"은 UI에 별도 필드가 없고 `followUp`이 그렇게 렌더링되는 것으로 저장소에서 확인했다(§4.5 근거 참고).

## 5. F1~F5 양성·음성 고정 요약 (1줄씩)

- **F1**: 프롬프트 전용(TEMPORAL STATE) — 음성 "계획을 완료 전제로 묻지 않음"·양성 "실제 발생한 반응/결과는 물어도 됨" 둘 다 프롬프트 문구 존재로 고정, 출력 검증기는 없음(모의 모델로는 시제 추론을 시험할 수 없어서).
- **F2**: 프롬프트 + 검증기(`script_contract`) — 음성 "개수/형식/followUp 위반 시 재생성·최종 자르기/제거" · 양성 "정확한 개수·형식이면 통과, 개수 미지정 질문은 3단 카드 무회귀" 모두 파이프라인 통합 테스트로 실동작 고정.
- **F3**: 프롬프트 강화 + F2 재사용 — 음성 "완성 출력엔 followUp 없음"은 F2의 followup 검증기가 실제로 집행, 나머지(근거부족 1개 허용/기답변 재질문 금지)는 문구 무회귀로 고정.
- **F4**: 프롬프트 전용(EVIDENCE FOR CLAIMS ABOUT THEM) — 음성 "말 안 한 취향/미래보장 금지"·양성 "말한 취향은 써도 됨, 강제 언급은 아님" 둘 다 프롬프트 문구 존재로 고정, 검증기는 없음(엔티티 매칭 없이는 과차단/과소검출 둘 다 위험해서).
- **F5**: 프롬프트 + 검증기(`hidden_truth_framing`) — 음성 "진짜 마음을 읽을 수 있어요"류 확정형·양성 "알 수는 없어요"류 부정형 모두 `validateAskAnswer` 단위 테스트 + POST 통합 테스트로 실동작 고정.

## 6. F5 검증기 상세 — 어떻게 잡았고 무엇을 일부러 안 잡았는가

- **방식**: 프롬프트 1차(NO HIDDEN-TRUTH FRAMING 블록) + 출력 검증기 2차(`findHiddenTruthFraming`), 지시서 §1 F5가 요구한 그대로.
- **최소 검출로 고른 패턴**: 관측된 SMOKE 결함(`진짜 마음`, `진짜 이유`)과 지시서 예문(`숨은 진심`, `속마음을 확정`)에 정확히 등장한 4개 복합어만 주제어로 삼았다 — 단어 하나(`진심`)는 일부러 안 잡았다. "그 사람 진심을 존중해주세요"처럼 흔한 선의의 표현까지 걸리는 과차단이 더 위험하다고 판단했기 때문이다.
- **판정 방식**: 같은 문장 안에 부정/한계 표현(`없`/`어렵`/`힘들`/`모르`/`아니`)이 있으면 무조건 통과시킨다 — "확정적 주장의 방향"만 보고 어휘 자체를 막지 않는다는 지시서 원칙을 그대로 구현한 것.
- **일부러 안 잡은 것**: 영어 표현(`I can tell their real feelings` 류)은 다루지 않았다 — 관측된 결함이 전부 한국어였고, 영어 대응 표현까지 다루면 최소 검출 범위를 넘어선다고 판단했다. 이는 알려진 한계로 남겨둔다.

## 7. 정직 보고

- **F1·F4는 검증기 없이 프롬프트 문구만으로 처리했다.** §4.5가 F2처럼 "기존 계약이 있는데 집행이 없다"는 명시적 증거를 제공한 항목이 아니었고, 모의(mock) LLM 테스트로는 실제 모델의 시제 추론이나 근거 판별을 검증할 수 없기 때문이다. 실제 억제 효과는 배포 후 SMOKE로만 확인 가능하다.
- **F2의 "개수 초과분 자르기" 최종 처분은 앞에서부터 N개를 남기고 뒤를 자른다.** 실제 관측된 결함(#4)이 뒤에 붙는 followUp/부연 문장이었으므로 이 방향을 택했지만, 만약 모델이 앞에 안내 문장을 붙이는 방식으로 실패한다면 이 처분이 잘못된 줄을 남길 수 있다 — 알려진 한계로 남겨둔다. followUp 관련 결함(#4)은 별도의 followUp-strip 처분으로 안전하게 커버된다.
- **F2의 "형식 위반"(번호·불릿·"/") 최종 처분은 자동 수정 없이 그대로 서빙한다** — 내용을 훼손할 위험이 있는 자동 수정보다 안전한 pass-through를 택했다. 재생성 1회에서 고쳐지지 않으면 다음 턴까지 남을 수 있다.
- **F4의 "사용자가 실제로 말한 취향" 판별은 코드로 강제하지 않는다** — 프롬프트가 요구할 뿐이며, 검증기가 이를 어기는 사례를 잡아내지 못한다. 지시서가 과차단을 명시적으로 실패로 규정했기 때문에, 판정 정확도가 낮은 얕은 검증기보다는 프롬프트 단독을 선택했다.
