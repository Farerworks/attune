## 2. 구현 요지

**색 역할 분리(v2 정본)** — v1은 선택 밑줄에 그 사람의 오행색을 썼는데, 이는 "점=정체성, 밑줄=선택 상태"라는 서로 다른 두 역할을 같은 색 축에 겹쳐 놓는 것이라는 외부 검토 지적을 받았다. v2에서는 점은 계속 오행색(`ELEMENT_COLORS[...].fg`, 비선택 시 `opacity 0.55`)을 쓰되, 선택 밑줄은 **모든 사람에 대해 동일하게 `var(--c-vermilion)`**(공통 상태색)로 고정했다. 선택 이름은 `var(--c-ink)` + `fontWeight 600`, 비선택 이름은 `var(--c-ink-body)`(muted 사용 금지 그대로 유지).

**터치 영역 — 버튼 자체가 44px을 보장** — v1은 칩을 담는 *행*에 `minHeight: 44`를 줘서 터치 영역을 보장했는데("행 높이로 보장"), 이는 행 레이아웃이 바뀌면 함께 깨질 수 있는 방식이라는 지적을 받았다. v2는 구조를 바꿨다: 버튼(`<button>`)이 `padding: '9px 2px', minHeight: 44`를 직접 갖고, 실제로 보이는 점+이름+밑줄은 그 버튼 **내부의 별도 `<span>` 래퍼**에 담아 시각적으로는 28~32px 높이만 차지하도록 했다 — 밑줄이 텍스트 바로 아래에 붙고, 보이지 않는 상하 여백이 버튼 자체의 히트 영역을 44px까지 늘려준다. 이제 행 자체엔 `minHeight`를 주지 않는다(v1의 `minHeight: 44`는 제거).

**접근성** — 각 탭 버튼에 `aria-pressed={active}`를 추가했다. 포커스 아웃라인을 억제하는 CSS를 새로 추가하지 않았다(기존 `.pressable` 클래스도 outline을 건드리지 않으므로 브라우저 기본 포커스 링이 그대로 유지된다). `tablist`/`tab` role 패턴 전체는 이번 판 범위 밖(백로그)으로 남겨뒀다.

**`+ Someone` 항상 표시** — v1은 저장된 사람이 1명이라도 있으면 `+ Someone`을 숨겼는데, 이는 대화 중에 사람을 추가할 경로를 잃어버리는 문제였다. v2는 `(hasAnyThread || !hasPersonChips)` 조건으로 바꿔, 대화가 있는 상태에서는 사람 수와 무관하게 행 끝에 항상 텍스트형 `+ Someone`(ink-body, 점·밑줄 없음)이 남는다. 첫 방문(빈 상태)에서는 기존 `!hasPersonChips` 조건 그대로(대시 상자 스타일 무변경).

**조건부·위치 인지 페이드** — 오버레이 방식(CSS mask 아님 — 글자를 실제로 잘라내지 않고 뒤에서 색만 흐리게 겹치는 방식)은 유지하되, `chipRowRef`의 `scrollLeft`/`scrollWidth`/`clientWidth`를 계산해 실제로 오버플로가 있을 때만, 그리고 현재 스크롤 위치에 따라 왼쪽·오른쪽 중 실제로 콘텐츠가 더 있는 쪽에만 표시한다(시작=오른쪽만, 중간=양쪽, 끝=왼쪽만). `onScroll` 핸들러와 `selected`/`chips` 변경 시 모두 재계산한다.

**scrollIntoView → scrollLeft 직접 조정** — v1은 선택된 칩 wrapper에 `element.scrollIntoView({ inline: 'nearest' })`를 호출했는데, 이는 브라우저 구현에 따라 세로축(`block`)이 기본값 `'start'`로 처리되어 페이지 전체가 세로로 점프할 수 있는 위험이 있다는 지적을 받았다(sticky 상단바라 대부분 무해하지만 보장은 아니다). v2는 `Element.scrollIntoView`를 전혀 쓰지 않는다 — 선택된 칩의 `offsetLeft`/`offsetWidth`와 컨테이너의 `scrollLeft`/`clientWidth`를 직접 비교해, 칩이 보이는 범위 밖일 때만 `container.scrollTo({ left, behavior })`로 **가로 컨테이너 자신만** 스크롤한다. `prefers-reduced-motion: reduce`이면 `behavior: 'auto'`(즉시 이동), 아니면 `'smooth'`.

**첫 방문(빈 상태)** — 대형 필+아바타 원+dashed `+ Someone`+캡션 모두 무변형. 코드상 `ChipButton`의 `default` 분기와 행의 `gap: 8`/`alignItems: 'flex-start'`가 그대로 유지된다.

## 3. 기존 대비 위반 카탈로그 (§3 요구 — 이번 판 수정 대상 아님)

첫 방문(빈 상태) 화면에 남아있는 8.5~13px `var(--c-muted)` 텍스트는 WCAG 4.5:1 대비 기준(muted는 이 팔레트에서 약 3.94:1로 미달)을 만족하지 못한다. 이번 판은 위 §1~2에서 명시한 탭형 전환만 다루므로 아래는 **수정하지 않고 후속 판(ink-body 교체 대상)으로만 등재**한다.

| 위치 | 텍스트 | 현재 색 |
|---|---|---|
| 대형 칩 캡션 | `YOU · TIMING · ANYTHING` / `ADD A PERSON` | `var(--c-muted)` |
| 상단 잔량 표기 | `N QUESTIONS LEFT TODAY` | `var(--c-muted)` |
| 하단 빠른 질문(quick prompt) 칩 | 예: `대화를 어떻게 이어가지?` | `var(--c-muted)` |
| 하단 고지(disclaimer) | `Attune is for understanding and self-reflection, not a verdict on anyone.` | `var(--c-muted)` |

## 4. 테스트

- 탭형: 배경 `transparent` / 버튼 `minHeight: 44px`(패딩 포함 히트 영역) / `aria-pressed` 선택 반영 / 선택 밑줄이 정확히 `2px solid var(--c-vermilion)`(오행색 아님) / 비선택 밑줄은 `2px solid transparent` / 비선택 이름 `var(--c-ink-body)`(≠`var(--c-muted)`) — 1건에 모두 포함.
- `+ Someone`: 사람 2명이 이미 저장된 상태에서도 행 끝에 존재 — 1건.
- 동작 무회귀: 사람 탭 전환 시 해당 사람의 스레드로 정확히 바뀌고 다른 사람 메시지는 안 보임 — 1건(신규). 사람 탭 전환 시 진행 중이던 안전 플로우(S1 카드)가 초기화되고 정상 입력창으로 돌아옴 — 1건(신규).
- 빈 시드: 대형 칩 `minHeight: 48px` 무변형 — 1건(유지).

## 5. 렌더 확인 — 6장 (실제 브라우저, Playwright, 390×844)

텔레그램으로 **전송함**.

1. 대화 중 2명(Me="윤" + 1명) — 선택된 "윤" 아래 밑줄이 vermilion(주황빛 빨강)임을 확인. `+ Someone`도 사람이 있는데 행 끝에 여전히 보임.
2. 6명 시드, 스크롤 시작 위치 — 처음 6명(Me+5)만 보이고 오른쪽에 더 있음.
3. 같은 6명 시드에서 마지막 사람("사람6") 탭 클릭 — **가로 컨테이너가 자동으로 오른쪽 끝까지 스크롤**되어 선택된 탭이 밑줄과 함께 보이고, 왼쪽 가장자리에 페이드(잘린 "2" 텍스트)가 보임 — scrollLeft 기반 이동과 위치 인지 페이드가 실제로 작동함을 확인.
4. 긴 한글 이름(예: "김민준하늘사랑") 2개 포함 — 줄바꿈 없이 한 줄로 렌더.
5. 긴 영문 이름("Christopher Alexander") 포함 — 동일하게 한 줄 유지.
6. 키보드 열림 시뮬레이션(가짜 `visualViewport` 이벤트) — 상단 ATTUNE+탭 행이 그대로 화면에 유지됨(BRIEF-094C-FIX의 기존 로직, 이번 판에서 손대지 않았음을 재확인).

## 7. 정직 보고

- **버튼 실측 높이 검증은 jsdom 한계로 "실측"이 아니라 인라인 스타일 값 확인이다.** jsdom은 실제 폰트 메트릭/레이아웃을 계산하지 않아 `getBoundingClientRect()`가 항상 0을 반환한다. 그래서 "버튼 실측 높이 ≥44px" 요구는 `style.minHeight === '44px'` 확인으로 대신했다 — 코드가 `minHeight: 44`를 직접 선언하므로 값 자체는 신뢰할 수 있지만, 실제 렌더된 픽셀 높이의 "측정"은 아니다. 실제 렌더 결과는 §5 스크린샷으로 육안 확인했다.
- **미감 최종 판정은 YS 실물**이라고 브리프 §5가 명시했다 — 이번 자가점검은 기능·구조 확인까지이고, 2명/6명 비교의 "예쁨" 여부 자체는 내가 판단할 수 없는 영역이다.
- 페이드가 실제로 위치 인지적으로 동작하는지는 스크린샷 ③에서 왼쪽 페이드가 "2" 텍스트를 가리는 모습으로 육안 확인했다 — v1 보고서에서 밝혔던 "페이드가 잘 안 보인다"는 우려는 스크롤이 실제로 발생한 상태에서는 해소됐다.
- §3의 muted 대비 카탈로그는 이번 판에서 손대지 않았다 — 지시서가 명시적으로 "수정 대상 아님"이라고 했기 때문이며, 후속 판에서 처리될 목록으로만 남겨둔다.
