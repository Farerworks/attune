## 2. 구현 요지

**상단 고정** — 기존에 `<TabTopBar right={<AccountAvatar/>} />`(self-closing)로만 쓰이던 걸, 칩+잔량 표기 블록을 `children`으로 넘겨 `<TabTopBar right={...}>{...}</TabTopBar>`로 바꿨다. `TabTopBar.tsx`는 `children`이 있으면 ATTUNE 행 바로 아래에 그대로 렌더하는 조건부 스타일(`marginBottom: children?10:0` 등)을 이미 갖추고 있었다 — **이 prop 자체는 수정하지 않았고, 사용법만 바꿨다.** 결과적으로 두 번째 `position: sticky` 요소를 새로 만들어 `top` 오프셋을 수동 계산(TabTopBar 실측 높이 + 가변 안전영역)하는 번거로움 없이, 기존 sticky 컨테이너 하나에 자연스럽게 편입됐다.

**하단 고정 + 키보드 결합** — 기존 `position: sticky; bottom: 0`은 그대로 두되(평상시), `useKeyboardOpen()`(BRIEF-085/086, 새 감지 로직 작성 없이 그대로 재사용)이 `true`일 때만 `position: fixed`로 전환하고 뷰포트 중앙 정렬(`left/right/margin/width/maxWidth`, TabBar와 동일 패턴)을 추가했다. 이렇게 나눈 이유: 평상시(키보드 닫힘)엔 `<main className="pb-safe">`가 이미 탭바 높이만큼 하단 여백을 예약해두므로 sticky만으로 탭바 위에 정확히 앉는다. 키보드가 열리면 탭바 자체가 숨어(기존 로직) 그 예약된 공간이 빈 채로 남는데, 이 상태에서까지 sticky를 유지하면 입력창과 키보드 사이에 탭바 높이만큼 불필요한 틈이 남는다 — 그래서 이때만 `fixed`로 바꿔 진짜 화면 하단에 붙인다.

**중간 스크롤** — 메시지 목록을 담은 `flex: 1` div는 그대로 두었다(082/385행대에서 이미 `flex:1`이었음) — 상하가 고정됨으로써 자동으로 이 영역만 스크롤 대상이 된다. 새 메시지 자동 스크롤(`bottomRef.scrollIntoView`)도 무변경.

**빈 스레드 첫 화면** — "Go ahead, ask." + 예시 카드 영역은 그대로 스크롤 영역 안에 있다(구조 무변경).

## 3. 발견·수정한 부수 문제

렌더 확인 중 Next.js dev 콘솔에서 React 경고를 하나 발견했다: `padding`(약칭)과 `paddingBottom`(개별 속성)을 같은 스타일 객체에 조건부로 섞어 쓰면 리렌더 시 "Updating a style property... can lead to styling bugs" 경고가 뜬다(하단 입력 영역의 키보드 열림/닫힘 전환에서 실제로 발생 확인). `padding` 약칭을 `paddingTop`/`paddingRight`/`paddingLeft`/`paddingBottom` 개별 속성으로 풀어써서 해결했다 — 시각적 결과는 동일하다.

## 6. 정직 보고

- 키보드 열림 시 입력창이 "키보드 바로 위"에 정확히 붙는지는 실제 iOS 온스크린 키보드가 없는 이 환경에서 검증할 수 없다. `useKeyboardOpen()`이 `true`가 됐을 때 레이아웃이 `fixed`로 전환되는 것까지는 확인했지만, 실제 키보드 높이와의 픽셀 단위 정합은 YS 실기기 확인이 필요하다(BRIEF-085/086 보고서에서도 동일하게 밝힌 한계).
- 키보드 열림 상태에서 스크롤 영역의 하단 패딩을 입력창의 정확한 렌더 높이에 맞춰 동적으로 재계산하지는 않았다 — 입력창이 `fixed`로 전환되며 문서 흐름에서 빠지는 순간, 만약 그 직후 사용자가 메시지 목록의 맨 아래를 보고 있었다면 아주 짧게 마지막 메시지 일부가 가려질 수 있다. 다만 키보드가 열리는 시점은 대개 사용자가 막 입력을 시작하는 시점이라 실사용 영향은 제한적이라고 판단해, 별도의 높이 측정 로직은 추가하지 않았다.
